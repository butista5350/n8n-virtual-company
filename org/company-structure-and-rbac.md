## 3) المبادئ الحاكمة

1. **أقل صلاحية:** لكل موظف الأدوات اللازمة لمهمته فقط.
2. **لا إنتاج ذاتي:** لا موظف افتراضي يفعّل شيئاً في الإنتاج أو ينفق أو ينشر خارجياً بمفرده.
3. **الفصل بين المنفّذ والرقيب:** مكتب الحوكمة والأمن لا ينفّذ ولا يكتب، ويتبع المدير العام مباشرة.
4. **الفرع:** كل ملف أو مسار جديد على `dev` فقط. الدمج إلى `main` عبر PR بعد موافقة صريحة. ممنوع التعديل المباشر على `main`.
5. **الفرض بالبنية لا بالتعليمات:** بوابة الموافقة تُوضع كعقدة إلزامية قبل أي أداة كتابة داخل المسار، ولا تُترك لالتزام الموظف بتعليماته.
6. **الفشل الآمن:** طلب موافقة بلا رد خلال 24 ساعة يُعتبر مرفوضاً.
7. **التتبع:** كل طلب موافقة وكل قرار يُسجَّل (من، ماذا، متى، النتيجة).
8. **تغيير هذا الملف:** أي تعديل عليه يمر بـPR وموافقة، لأنه يعادل تغيير السياسة.
9. **اقتصاد النماذج:** المنطق البرمجي أولاً، ثم نموذج صغير، ثم متوسط. وClaude مقصور على التخطيط المعماري وتصميم المسارات وكتابة الأكواد ومراجعتها (القسم 7.1).

**قواعد إضافية للنشر:**
- لا نص منسوخ من مصادر محمية، ولا ألغاز مأخوذة من كتب أخرى، ولا علامات تجارية في العنوان أو الكلمات المفتاحية.
- قوائم الكلمات (Word Search) أصلية ومصنّفة بمواضيع، تُصفّى آلياً من الكلمات غير اللائقة والمكررة، ولا تُنسخ من كتب أو مواقع.
- الخطوط المستخدمة في الداخل والغلاف مفتوحة الترخيص أو مضمّنة مع المكتبة المستخدمة، ولا خطوط تجارية.
- يُجهَّز بند الإفصاح عن المحتوى المولَّد بالذكاء الاصطناعي ضمن نموذج الرفع، ويقرر المدير العام الإجابة النهائية عند الرفع.
- لا كتاب يُحسب جاهزاً إذا تكرر محتواه أو قارب كتاباً سابقاً للشركة (فحص تكرار ضمن قائمة التحقق).

## 7.1) سياسة توجيه النماذج (Model Routing Policy)

**القرار:** يُقصر استخدام Claude على **التخطيط المعماري، وتصميم المسارات، وكتابة الأكواد ومراجعتها**. كل الوظائف التشغيلية الأخرى (مراقبة، فحص، صياغة، عمليات روتينية) تُصمَّم لتعمل بنموذج أقل تكلفة، أو **بمنطق برمجي مباشر بلا نموذج** متى أمكن.

### المستويات

| المستوى | الوصف | الاستخدام |
|---|---|---|
| **T0** | بلا نموذج لغوي: Code وIF وRegex واستدعاءات API ومقارنات | **الافتراضي** لكل ما يمكن التعبير عنه بقاعدة واضحة |
| **T1** | نموذج صغير منخفض التكلفة | مهام روتينية قصيرة: تلخيص، قوائم كلمات، صياغة من قالب |
| **T2** | نموذج متوسط | كتابة أو تحليل يؤثر على جودة المنتج، بعدد استدعاءات محدود |
| **T3** | Claude (الفئة العليا) | تخطيط معماري، تصميم مسارات، كتابة ومراجعة أكواد، **في جلسات التطوير فقط** |

### النموذج الموصى به لكل مقعد مفعّل (المرحلة 1)

| # | المقعد | المستوى | ما الذي يُنفَّذ به وقت التشغيل | القيود |
|---|---|---|---|---|

| 2 | المراقب المالي والمخاطر | **T0** | حساب الاستهلاك ومقارنته بالحدود (5$ يومياً) بلا نموذج | لا نموذج |
| 3 | مسؤول الأمن | **T0** | فحص الأسرار بأنماط Regex على فروقات PR وأسماء الاعتمادات | **لا نموذج أبداً**، حتى لا تصل أسرار محتملة إلى مزوّد خارجي |
| 4 | مهندس مسارات n8n | **T3 وقت التطوير فقط** | Claude يصمم المسارات ويكتب الأكواد ويراجعها في جلسات البناء. لا يوجد نموذج يعمل لهذا المقعد وقت التشغيل | لا مسار مجدول يستدعي T3 |
| 5 | مراقب الصحة والتنبيهات | **T0** | كل فحوصه برمجية (PR-1 بلا أي عقدة نموذج، وتتحقق الاختبارات من ذلك) | لا نموذج |

### القواعد

1. **T3 للتطوير فقط:** لا مسار مجدول أو تشغيلي يستدعي Claude من الفئة العليا. استخدامه في جلسات بناء المسارات وكتابة الأكواد ومراجعتها.
2. **البرمجة قبل النموذج:** أي خطوة يمكن كتابتها كقاعدة أو كود تكون T0. ولا تُضاف عقدة نموذج دون سطر تبرير في ملاحظات العقدة.
3. **إعلان المستوى:** كل عقدة نموذج تحمل في ملاحظاتها `Tier: T1/T2` وسبب استخدامها.
4. **أسماء النماذج في Config فقط:** يُضبط اسم النموذج لكل مستوى في عقدة `Config` لكل مسار (مكان واحد)، ولا يُكتب في عدة عقد. وتتغير الأسماء دون تعديل المنطق.
5. **سقوف:** حد أقصى لعدد الاستدعاءات لكل تشغيل، وللمخرجات (tokens) لكل استدعاء، يُعلن في `Config`. تجاوزه يوقف الخطوة ويُنبّه المدير العام.
6. **الترقية بين المستويات:** من T1 إلى T2 أو من T2 إلى T3 تتطلب فشلاً موثّقاً في الجودة (محاولتان فاشلتان أو فشل قائمة التحقق) **وموافقة عبر `request_ceo_approval`**. أما التخفيض فيجوز بعد اختبار مقارنة على 20 عينة على الأقل، وبموافقة.
7. **لا أسرار في الأوامر (Prompts):** لا اعتمادات ولا مفاتيح ولا بيانات حسابات تُرسل إلى أي نموذج. تُرسل البيانات اللازمة للمهمة فقط.
8. **قياس الاستهلاك:** كل عقدة نموذج تسجّل اسم النموذج وعدد الرموز المُدخلة والمُخرجة، ويقرأها المراقب المالي. وتنبيه 5$ يومياً يشمل مجموع كل المستويات.
9. **اختيار النماذج:** لا تُثبَّت أسماء نماذج أو أسعار في هذا الملف، لأن الأسعار تتغير. تُختار بعد **اختبار مقارنة صغير** (مثلاً 20 عينة من مهمة المؤلف وكاتب SEO) يقيس الجودة والكلفة، ثم تُسجَّل في `Config`.
10. **المراجعة:** تُعاد المقارنة كل ربع سنة، أو عند صدور نموذج جديد بسعر أو جودة مختلفة.

## 11) تأمين المستودع: Fine-grained Token وحماية `main` (قرار معتمد)

الهدف: أن تُفرض القاعدة «لا تعديل مباشر على `main`» بإعدادات GitHub نفسها، لا بالتعليمات وحدها.

### 11.1 الاعتماد (Token)

| البند | الإعداد |
|---|---|
| النوع | Fine-grained personal access token (وليس Classic) |
| نطاق المستودعات | **Only select repositories** ← `butista5350/n8n-virtual-company` فقط |
| الصلاحيات | `Contents: Read and write` + `Pull requests: Read and write` (+ `Metadata: Read-only` تلقائياً) |
| ممنوع منحه | Administration، Workflows، Secrets، Actions، Webhooks، أي مستودع آخر |
| مدة الصلاحية | 90 يوماً كحد أقصى، مع تذكير بالتجديد قبل 7 أيام من الانتهاء |
| الحساب | إن كان `GitHub account 2` حساباً ثانياً: يُدعى **Collaborator بدور Write** وليس Admin. إن كان حسابك الرئيسي، فاعتمد قاعدة الحماية 11.2 بقائمة تجاوز فارغة |
| التخزين | يُحفظ في Credentials داخل n8n فقط، ولا يظهر في المستودع أو في الرسائل أو السجلات |
| التدوير | يُستبدل فوراً عند أي اشتباه بتسريب، ويقرر المدير العام ذلك بناءً على إنذار مسؤول الأمن |

### 11.2 حماية الفرع `main` (Ruleset)

المسار في GitHub: Repository ← Settings ← Rules ← Rulesets ← New branch ruleset.

| القاعدة | الإعداد |
|---|---|
| الفرع المستهدف | `main` |
| Require a pull request before merging | مفعّل، وعدد الموافقات المطلوبة **0** (لأن الـPR تنشئه أداة بحسابك ولا يمكنك الموافقة على طلبك؛ زر الدمج بيدك هو الموافقة، وقبله `request_ceo_approval`) |
| Block force pushes | مفعّل |
| Restrict deletions | مفعّل |
| Bypass list | **فارغة** (بلا استثناءات، حتى للمالك) |
| طريقة الدمج | **Create a merge commit** (وليس Squash) حتى لا ينفصل تاريخ `dev` عن `main` |

**ملاحظة:** الحماية عبر Rulesets على المستودعات **الخاصة** قد تتطلب خطة GitHub مدفوعة. إن لم تتوفر في خطتك، فاجعل المستودع عاماً (إن كان محتواه لا يتضمن أسراراً) أو أبقِ الحماية الوحيدة هي اعتماد Collaborator بدور Write مع فرع `main` مقيّد بأي وسيلة متاحة، وسجّل ذلك هنا كفجوة مقبولة.

### 11.3 اختبار الإغلاق (يُنفَّذ بعد التطبيق)

1. دفع مباشر إلى `main` بالـToken الجديد: `git push origin HEAD:main` ← **يجب أن يُرفض**.
2. قراءة أي مستودع آخر بالـToken ← **يجب أن يفشل**.
3. محاولة تغيير إعدادات المستودع (مثلاً عبر API) بالـToken ← **يجب أن تفشل**.
4. فتح PR من `dev` إلى `main` بالـToken ← **يجب أن ينجح**.
5. تسجيل نتيجة الاختبارات الأربعة في `status` أو ملاحظة PR-0.
